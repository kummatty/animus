## Summary
**Netfilter** is the in-kernel framework where packet **filtering** and **NAT**
happen; **nftables** is the modern userspace tool that programs it (replacing
`iptables`). As a packet travels through the kernel it passes fixed checkpoints called
**hooks** (`prerouting`, `input`, `forward`, `output`, `postrouting`). You attach
**chains** of **rules** to these hooks; each rule is a list of **match** conditions
plus an **action/verdict** (`accept`, `drop`, `masquerade`, …). The **`forward`** hook
handles packets the host **routes through itself** (exactly the VM↔internet case), so
a small **stateful** set of forward rules — "accept `established,related`" plus "accept
`new` from the trusted side" — is what lets a VM's traffic *and its replies* pass
through the host.

## Details

### The hooks — a packet's checkpoints
Every packet passes through fixed points where rules can run:

```
            ┌─ input ─────► (delivered to a local process)
prerouting ─┤
            └─ forward ───► postrouting ─► (out an interface)
(local process) ─ output ─► postrouting ─► (out an interface)
```

- **prerouting** — just arrived, before the routing decision.
- **input** — destined for *this host*.
- **forward** — *routed through* this host to another interface (the VM↔internet case).
- **output** — generated by this host.
- **postrouting** — last stop before leaving. **Source NAT/masquerade goes here.**

So you filter forwarded VM traffic at **forward**, and rewrite its source at
**postrouting**.

### nftables structure: table → chain → rule → statement
- **Table** — a namespace bound to an address **family** (e.g. `ip` = IPv4). Holds chains.
- **Chain** — an ordered list of rules. A **base chain** *hooks into the kernel* and
  declares `type` (filter / nat) + `hook` + `priority` + `policy`; a regular chain is
  just a jump target. The **priority** orders multiple base chains on the same hook;
  the **policy** is the default verdict if no rule matches (`accept`/`drop`).
- **Rule** — an ordered list of **statements**, evaluated top to bottom.
- **Statement** — either a **match** (a comparison `left <op> right`, where `left`
  extracts something from the packet — a header field, a meta attribute, or a conntrack
  value) or an **action/verdict** (`accept`, `drop`, `masquerade`, …).

A rule reads as: *if all matches pass, run the action.*

### The forward chain and the stateful idiom
The job: permit VM traffic to be routed through the host, in both directions.

```
ct state established,related  accept   # ongoing conversations + all replies
iifname <bridge>              accept   # NEW outbound flows from the trusted (VM) side
oifname <bridge>              accept   # traffic heading toward the VMs
```

- **`ct state established,related accept`** is the key rule for **return traffic**: a
  reply from the internet arrives on the *uplink* (not the VM side), so the
  `iifname` rule wouldn't match it — but conntrack marks it `established`, and this
  rule lets it back through. You decide on the `new` packet once; this fast-paths the
  rest.
- With **`policy drop`** these accepts are load-bearing (default-deny + explicit
  allows). With **`policy accept`** they're mostly intent/scaffolding — traffic flows
  anyway — and become essential the moment you switch to drop.

### Verdicts across multiple chains (the Docker/firewalld gotcha)
Several base chains can sit on the same hook (yours, Docker's, firewalld's). They all
run, and **`drop` is terminal** — an `accept` in *your* chain does **not** override a
`drop` in someone else's. That's why Docker/firewalld installing a `forward` chain
with a **drop policy** can silently black-hole VM egress even when NAT and ip_forward
look correct — so robust setups *detect a foreign force-drop and refuse*, rather than
adding an accept and assuming it worked.

### Jargon, glossed simply
- **netfilter** — the kernel framework for filtering and NAT.
- **nftables** — the modern tool to program netfilter (successor to iptables).
- **hook** — a fixed checkpoint in the packet's path where rules run.
- **chain** — an ordered list of rules; a *base* chain attaches to a hook.
- **base vs regular chain** — base hooks into the kernel (type+hook+priority+policy); regular is just a jump target.
- **rule** — an ordered list of statements (matches + action).
- **match** — a condition: `left <op> right` (e.g. `ip saddr == 10.42.0.0/16`).
- **verdict / action** — what to do: accept, drop, masquerade, …
- **policy** — a base chain's default verdict if nothing matches.
- **priority** — ordering among base chains on the same hook.
- **iifname / oifname** — the input / output interface *name* (at L3, the bridge — not a TAP).
- **ct state** — the conntrack state match (new/established/related/invalid).

## Key points
- Netfilter is the kernel filtering/NAT framework; nftables is the modern tool that programs it (replacing iptables).
- A packet passes fixed hooks: prerouting, input, forward, output, postrouting.
- `forward` handles packets routed *through* the host (VM↔internet); source NAT/masquerade goes at `postrouting`.
- nftables nests as table → chain → rule → statement; a statement is a match (`left op right`) or an action/verdict.
- A base chain hooks into the kernel with type + hook + priority + policy; policy is the default verdict, priority orders base chains on a hook.
- The stateful forward idiom: accept `established,related` (continues approved flows + replies) plus accept `new` from the trusted side.
- `ct state established,related accept` is what admits internet→VM replies, since replies arrive from the uplink, not the VM side.
- With policy=accept the forward accepts are mostly intent; with policy=drop they're the actual allow-list.
- Multiple base chains share a hook; `drop` is terminal, so your `accept` can't override another chain's `drop` — hence Docker/firewalld forward-drops silently black-hole VM egress.
